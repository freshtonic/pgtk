# Target versions: PostgreSQL 14 to 19

Date: 2026-09-22. Decision record: ADR 0009. Terms: `CONTEXT.md` (target
version, version feature, version parity, version gate). SQL research:
`docs/research/postgres-14-19-sql-syntax-changes.md`.

## Goal

A pg-sql build and a pg-psql build reproduce the raw parser and the psql
lexer of one target version. The version features `pg14`, `pg15`, `pg16`,
`pg17`, `pg18` and `pg19-beta` are mutually exclusive. `pg17` is the default.

## Decisions

1. **Enforcement.** `compile_error!` stops a build that has zero, or two or
   more, `pgNN` features. The message names feature unification and
   `default-features = false`. A `since-*` feature without a `pgNN` feature
   is also an error.
2. **Version gates.** `pgNN` enables `since-pg15` … `since-pgNN`. "Added in N"
   is `feature = "since-pgN"`. "Removed in N" is `not(feature = "since-pgN")`.
   There is no `since-pg14`. Every gate cites the research entry, or the
   `gram.y`/`scan.l`/`psqlscan.l` change.
3. **Keywords.** A keyword that changes category or label status gets two
   `tokens!` entries with opposite `cfg`. Codegen reports an error when two
   active entries have the same name. The `categories`, `flags` and
   `admissions` sections have no `cfg`.
4. **Scoped LR resolutions** take `cfg`. A resolution that matches nothing in
   the active grammar is still an error.
5. **AST shape.** Prefer additive changes (a gated variant or field). Change
   the type of a field between versions only when `gram.y` makes the shapes
   incompatible.
6. **Code layout.** A statement or large subgrammar that exists only in some
   versions gets its own module. The module is gated at `mod` and at the
   variant that refers to it. A clause-sized change stays inline.
7. **Run-time report.** `pub const TARGET_VERSION: TargetVersion`. There is
   no run-time version selection.
8. **Intermediate crates.** `pg-psql` uses `default-features = false` on its
   `pg-sql` dependency and forwards the version features. `CLAUDE.md` gets a
   rule for future intermediate crates.
9. **Oracle.** `pg-oracle/scripts/build-pg.sh` builds a worktree of the
   pinned tag for each target version (for example `target/pg-trees/REL_16_15`).
   `pg-oracle` gets the version features, and `postgres-oracle` forwards them.
10. **Differential baseline.** One baseline file for each target version, with
    the same corpus, generated by that version's oracle.
11. **Embedded tests.** `embedded-tests/inventory.tsv` gets a version-range
    column. `tests/embedded_inventory.rs` pins one count for each version.
    Every "removed in N" change gets an explicit negative test.
12. **pg-psql parity** covers only `psqlscan.l` lexing and the send commands.
    Meta-commands in the catch-all `MetaCommand` token have no version gate
    until #11–#13 model them. pg-psql version differences get explicit tests
    gated with `since-*`.
13. **Gate.** The merge gate runs all six versions with `spans`, and the
    no-`spans` and `arbitrary` combinations on `pg17` only. The local edit
    loop uses `pg17`.
14. **Principle 5** in `CLAUDE.md` changes to "test against the target
    version's raw-parser oracle".

## Non-goals

- `standard_conforming_strings = off` lexing.
- Rejections that come from execution, the catalog or parse analysis.
- Diagnostics that know about versions. A `pg17` build rejects 18 syntax as
  PostgreSQL 17 does.
- Version gates on psql meta-commands that pg-psql does not parse.

## Increments

Each increment is one branch and one GitHub issue. The gate must be green before
the merge.

1. **recursa: `cfg` for keywords and resolutions** (freshtonic/recursa#133). `#[cfg]` on `keywords`
   entries in `tokens!`, the duplicate-active-name error, and `#[cfg]` on
   scoped LR resolutions. Tests in recursa-codegen.
2. **Move the 17 pin to 17.11** (#71). Move the submodule, rebuild the oracle and
   regenerate the differential baseline. Examine every outcome change. This
   comes before the feature work, so each baseline change has one cause.
3. **psql research** (#72). `docs/research/psql-14-19-syntax-changes.md`, with the
   same method as the SQL research and the pins above. It covers
   `psqlscan.l`, `psqlscanslash.l`, the meta-commands in `command.c`, and the
   psql sections of the release notes. It includes back-patched changes such
   as `\restrict`. Increments 1, 2 and 3 can run in parallel.
4. **Infrastructure** (#73). Version and `since-*` features in `pg-sql`, `pg-psql`
   and `pg-oracle`. The enforcement, `TARGET_VERSION`, oracle trees for each
   version, baselines for each version, the ledger column, the six-version
   gate, and the `CLAUDE.md` changes (principle 5, principle 8 ledgers,
   intermediate crates). There is no grammar change: the `pg17` behavior is
   the same, and the other versions build but have 17 grammar until their
   increments land.
5. **`pg16`** (#74). Gate out what 17 added (SQL/JSON query functions and
   `JSON_TABLE`, the MERGE `BY SOURCE`/`RETURNING` clauses, `AT LOCAL`, the
   17 keywords and the `json` category) and restore what 17 changed. Also the
   16 psql differences.
6. **`pg15`** (#75). Also gate out the 16 additions (SQL/JSON constructors, `IS
   JSON`, non-decimal and underscore literals, `FORMAT_LA`, `SYSTEM_USER`).
7. **`pg14`** (#76). Also gate out the 15 additions (`MERGE`, publication objects,
   `NULLS NOT DISTINCT`), and restore the lexing without the trailing-junk
   check (`123abc` is `123 AS abc`).
8. **`pg18`** (#77). Add the 18 syntax from the research ("Notes for pg-sql") and
   remove `RECHECK`.
9. **`pg19-beta`** (#78). First compare `REL_19_STABLE` at `b73d13c` with the
   research snapshot `7a74e5ed92d`. Then add the 19 syntax and the AS_LABEL
   status of `ignore` and `respect`. The comparison showed that `b73d13c`
   reverts SQL/PGQ (with the `RIGHT_ARROW` and `|` tokens), `FOR PORTION OF`
   and the new `CREATE SCHEMA` elements, so the increment does not add them.
10. **Follow-up: psqlscan oracle** (#79). An FFI oracle for the psql lexer, built
    from the tree for each version. This does not block increments 5 to 9.
