# 1. Dual build with Buck2 and Cargo

## Status

Accepted (2026-10-14)

## Context

pgtk must build with Buck2. It must also build with vanilla Cargo, so that crates.io users and
Rust tooling (rust-analyzer, `cargo publish`) work as usual. The two build systems must not
clobber each other.

## Decision

- **Exported crate**: a crate that is published to crates.io and has Buck
  `visibility = ["PUBLIC"]`. The exported crates are `pgtk-sql`, `pgtk-analyze`, `pgtk-catalog` and
  `pgtk-proto`.
- **Internal crate**: a crate with `publish = false` and no PUBLIC visibility.
- There is one `Cargo.lock`, at the workspace root. Both builds use it. Only `cargo` changes it.
  Reindeer reads it with `--locked`. Thus Cargo and Buck always use the same third-party versions.
- Each third-party version is declared once, in the root `[workspace.dependencies]`.
- Reindeer reads the root `Cargo.toml` (the reindeer "hybrid" layout). It vendors the third-party
  sources into `third-party/rust/vendor/` and generates `third-party/rust/BUCK`. Both are committed.
  Buck builds are thus offline and hermetic.
- Cargo gets crates from crates.io. There is no source replacement at the root.
- The BUCK file of each first-party crate is written by hand.
- **Cargo-only crate**: a crate with no BUCK file. The Cargo-only crates are `pgtk-oracle`,
  `pgtk-psql-oracle` and `pgtk-catalog-xtask`. The oracles link a PostgreSQL build from a cache
  outside the repository, so Buck cannot build them hermetically. `pgtk-catalog-xtask` is a
  maintenance tool.
- Buck builds one feature set for each crate: the default features. `pgtk-sql` also has `spans`,
  because `pgtk-psql` and `pgtk-analyze` need it. The other Target Versions and the oracle
  features are Cargo-only.
- A first-party build script that uses recursa-codegen runs through `first_party_build_script`
  (`tools/rust/build_script.bzl`), not the prelude `buildscript_run`. recursa-codegen does not
  accept a symlink in a source path, and it reads `CARGO_CFG_FEATURE`, which `buildscript_run`
  does not set.
- A first-party crate gets reindeer fixups too, because reindeer requires a build-script decision
  for each workspace member. Reindeer generates no rules for a workspace member.
- A third-party crate with a build script must have a fixup (`unresolved_fixup_error = true`).
- `rust-toolchain.toml` pins rustc for both builds. Buck uses the system Rust toolchain.
- `tools/buck2` (dotslash) pins buck2. The prelude is the copy that is bundled with buck2.

### Non-clobber rules

1. Cargo writes only to `target/`. Buck writes only to `buck-out/`.
2. No file is generated by one tool and edited by the other tool.
3. Cargo ignores BUCK files. Buck reads `Cargo.toml` only through reindeer.
4. A tool never changes `Cargo.lock` as a side effect.

## Consequences

- When you add or change a third-party dependency, you must run `scripts/update-third-party` and
  commit the vendored sources. CI fails if you forget.
- The deps in a first-party BUCK file can drift from its `Cargo.toml`. A missing dep makes the Buck
  build fail in CI. An extra dep is not found.
- The repository is larger because of the vendored sources.
- Buck supports only macOS arm64 and Linux x86_64. Add a `[platform.*]` table in `reindeer.toml`
  to support more.
